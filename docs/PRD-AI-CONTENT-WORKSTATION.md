## 1. 产品结论

AdgaiWalker MVP 不是通用自媒体操作系统，也不是 Skill/MCP 插件平台。它首先验证一个明确承诺：

> 作者完成核心观点和初稿后，系统能够可靠地完成加工、检查、封面、公众号排版、统一审批和双平台发布准备；任何自动化失败都不要求整篇重来。

MVP 只建设完成这条用户旅程所需的产品行为。问题调查、复杂选题评分、通用工具安装、全平台分发和自动数据回收保留为后续能力。

## 2. 当前结论锚点

本 PRD 依据以下已确认结论重写；后续范围判断以本节为准。

1. 目标是最短距离验证完整作品闭环，不是一次建设完整九模块经营平台。
2. 人负责选题主选、核心观点、初稿、最终审批和公众号公开确认。
3. AI 负责初稿后的结构加工、质量检查、封面制作、公众号排版、发布准备和复盘辅助。
4. 一篇作品是用户看到的中心对象；Clue、Seed、Execution、Submission 和 Publication 是底层业务对象。
5. 选题管理必须存在，但 MVP 只提供记录、候选、人工主选和归档，不自动研究和复杂评分。
6. Action 的计划日期可以为空；它同时承担备忘录、自由排期和视频记录。
7. P0 使用固定工具组合，不建设工具中心、通用安装器或插件市场。
8. 工具必须在技术上可替换，但 MVP 通过 Adapter 和配置实现，不通过用户界面实现。
9. 原稿和每个成功阶段的 Artifact 永不被后续阶段覆盖。
10. 兜底顺序固定为自动重试、使用已配置替代实现、人工接管当前阶段、导出完整作品包。
11. 网站和公众号独立记录发布状态；一个平台失败不影响另一个平台的成功结果。
12. 不伪造认证，不破解验证码，不规避平台风控，不绕过账号权限。

## 3. 背景与问题

### 3.1 当前行为

作者能够自己形成选题、观点和初稿，但初稿之后仍需反复完成：

- 调整结构与语言；
- 检查事实、隐私和夸大表达；
- 制作不同尺寸的封面；
- 将正文转换成公众号可用排版；
- 在网站与公众号之间重复填写；
- 工具失败后寻找上一次可用文件；
- 发布后手工记录反馈和下一步行动。

### 3.2 核心问题

现有困难不是缺少更多内容管理模块，而是没有一条可靠的“初稿到成品”流水线。自动化价值无法被验证，因为作品、工具输出、人工审核和发布结果没有形成同一条可恢复链路。

### 3.3 产品机会

把初稿之后的重复劳动压缩成一次启动、一次集中审核和一次发布确认，让作者把主要精力留给观点、表达和真实用户问题。

## 4. 目标用户与核心任务

### 4.1 目标用户

每周可投入 10–20 小时、主要独立经营内容业务的作者。他能够写出自己的观点和初稿，但不希望重复完成制作、排版和平台搬运。

### 4.2 核心任务

当作者完成一个初稿时，他希望：

1. 一次上传原稿和相关素材；
2. 明确告诉 AI 哪些观点不能改变；
3. 让系统完成固定的加工流程；
4. 在一个页面看到修改、风险、封面和平台预览；
5. 批准后完成网站发布和公众号草稿准备；
6. 任一阶段失败时只处理当前阶段；
7. 发布后记录最小结果并回收到下一轮选题。

## 5. MVP 目标与验证

### 5.1 产品目标

1. 证明人工初稿可以稳定转换为双平台成品。
2. 将初稿后的人工操作集中到必要补充、最终审批和公众号公开确认。
3. 证明固定工具组合足以连续服务三篇真实作品。
4. 证明自动化失败时仍能保住业务结果并继续工作。

### 5.2 首个证明点

使用一篇真实初稿完成：

```text
上传原稿和素材
→ AI 加工与检查
→ 生成双封面、网站稿和公众号稿
→ 作者统一审批
→ 网站发布
→ 公众号形成待确认草稿
→ 保存发布与反馈记录
```

### 5.3 MVP 完成指标

| 指标 | 验收线 |
|---|---|
| 真实作品 | 连续完成三篇，不使用演示样例稿 |
| 人工重复输入 | 标题、正文和摘要不在不同阶段重复录入 |
| 人工操作时间 | 初稿上传后，作者主动操作累计不超过 15 分钟，不含等待外部平台响应 |
| 审批集中度 | 正常情况下每篇只进行一次集中成品审批 |
| 网站结果 | 三篇均有可访问的正式 URL |
| 公众号结果 | 三篇均生成完整 HTML、图片、封面和字段清单；正常登录会话可保存为草稿 |
| 观点保护 | 未出现未经说明的核心观点改变 |
| 失败恢复 | 一次模拟阶段失败后从最近成功 Artifact 继续，不重跑已成功阶段 |
| 业务兜底 | 在 AI 不可用时仍可导出并人工完成发布 |

### 5.4 推翻条件

完成三篇作品后，出现以下任一结果时，不继续按当前路线扩建：

- 超过一半人工时间花在初稿前的问题调查和选题判断，说明上游洞察应提前进入下一阶段；
- 三篇作品都需要不同工具组合，说明固定 Adapter 不足，应提前建设能力注册；
- AI 加工后的主要内容连续两篇需要人工重做，说明生产流程尚未产生有效价值；
- 发布自动化节省的时间少于维护它的时间，说明应维持成品包导出而非继续自动化页面操作。

## 6. 产品范围

### 6.1 P0 范围

- 轻量选题池和人工主选；
- 无日期待办、自由排期、勾选和视频类型记录；
- 创建作品、上传初稿和素材；
- 核心观点保护和只读原稿；
- 固定 AI 生产流程；
- 分阶段 Artifact、进度、重试和人工接管；
- 双封面、网站 Markdown 和公众号 HTML；
- 集中审批、退回和批准版本冻结；
- 网站发布、公众号草稿辅助和独立状态；
- 完整作品包导出；
- 最小数据、真实完成结果和反馈回流。

### 6.2 明确不进入 P0

- AI 自动发现问题、联网调查、证据聚类和七维选题评分；
- 通用 ToolInstallation、工具中心、插件安装器和插件市场；
- 用户可配置 Recipe 编辑器；
- MCP 管理界面、远程 Tool Runner 和完整安全沙箱；
- 日历拖拽、惯性动画和复杂周期计划；
- 多人协作、角色权限和云端管理后台；
- 小红书、抖音、B 站和 X 的自动发布；
- 全平台数据自动回收和复杂经营看板；
- 客户、订单、报价、合同和财务；
- 第二套 AI 引擎；
- 未经审核自动改变核心观点或直接公开发布；
- 规避平台权限、验证码或风控。

### 6.3 后续边界

当三篇作品验证通过后，按实际瓶颈选择下一项，而不是同时扩建：

1. 上游瓶颈明显：增加 AI 问题调查和选题评分；
2. 工具差异明显：增加 capability 注册和工具管理；
3. 排期压力明显：增加日历视图和拖动排期；
4. 数据回收压力明显：增加已授权平台的数据连接；
5. 内容复用需求明显：增加多平台转译和分发。

## 7. 非协商原则

1. **人保留创作主体。** AI 不能替用户主选，也不能隐式改变核心观点。
2. **一篇作品一条时间线。** 用户不需要跨多个技术对象追踪同一作品。
3. **原稿不覆盖。** 所有加工结果写入新 Artifact。
4. **批准版本唯一。** 发布器只消费作者批准的 Artifact 哈希。
5. **阶段可恢复。** 一个阶段失败不重做已成功阶段。
6. **排期可选。** 未设置日期是正常状态，不显示为逾期。
7. **平台独立。** 网站与公众号分别成功、等待或失败。
8. **无 AI 也能完成。** 每篇作品始终可以人工接管和完整导出。
9. **业务阶段稳定，工具实现可替换。** P0 不把具体工具写进业务状态。

## 8. 人与 AI 的责任边界

| 环节 | 人负责 | AI 负责 |
|---|---|---|
| 选题 | 记录、判断、主选和归档 | P0 不自动主选 |
| 初稿 | 核心观点、个人经历、第一版表达 | 提供固定表单，不代替作者形成主体表达 |
| 内容加工 | 回答必要问题，判断实质修改 | 结构调整、语言整理、事实风险提示和质量检查 |
| 视觉与排版 | 审查标题、封面和品牌一致性 | 生成双封面、网站稿和公众号 HTML |
| 审批 | 批准、退回、恢复和取消 | 展示差异、风险和预览 |
| 发布 | 确认公众号公开，处理平台要求的真人验证 | 网站发布、公众号草稿辅助、结果记录 |
| 反馈 | 判断哪些反馈值得进入下一轮 | 整理数据与建议，不自动改变经营方向 |

## 9. 信息架构

P0 主导航只保留四个入口：

```text
工作台
作品
审批
发布
```

| 页面 | 包含内容 | 用户主要决策 |
|---|---|---|
| 工作台 | 选题收件箱、候选、已选定、Action、视频记录、AI 运行状态 | 做什么、何时做、是否完成 |
| 作品 | 原稿、素材、核心观点、生产阶段、Artifact 和失败恢复 | 启动、补充、重试或接管 |
| 审批 | 修改摘要、风险、双封面、网站预览和公众号预览 | 批准、退回或恢复 |
| 发布 | 网站与公众号独立状态、URL、导出和最小反馈 | 发布、重试、导出或记录结果 |

品牌资料和固定工具配置属于辅助设置，不进入主导航。

## 10. 端到端用户流程

### 10.1 从选题开始

```text
记录一个问题或题目
→ 进入候选池
→ 作者人工主选
→ 创建关联 Execution、内容任务书和无日期 Action
→ 作者完成初稿
→ 创建作品
```

### 10.2 从现有初稿开始

```text
点击“开始制作”
→ 录入最小题目信息并确认是人工主选
→ 自动建立底层关联对象
→ 上传初稿和素材
→ 创建作品
```

### 10.3 AI 生产与审批

```text
保存只读原稿
→ 结构和语言加工
→ 事实、隐私、夸大和观点偏移检查
→ 冻结候选正文
→ 生成双封面
→ 生成网站 Markdown 和公众号 HTML
→ 集中审批
```

### 10.4 发布与回流

```text
批准 Artifact
→ 网站发布与公众号草稿辅助独立执行
→ 记录 URL、草稿状态和失败原因
→ 录入最小数据、真实完成结果和反馈
→ 反馈可转为新选题或 Action
```

本 PRD 只有 15 项 P0。任何新增 P0 必须替换现有项目，不能直接扩张总数。

| ID | 需求 | 用户价值 | 可验证验收 |

## 12. 核心行为细则

### 12.1 选题与行动

- 选题只提供 `INBOX`、`CANDIDATE`、`SELECTED`、`ARCHIVED` 四个用户可见状态。
- MVP 不展示 AI 综合分；作者可以填写一句“为什么现在做”。
- 主选动作生成内容任务书，最少包含目标用户、场景、问题、核心追问和预期行动。
- AI 创建的 Action 默认无日期，并显示来源与关联作品。
- P0 通过日期选择器排期，不支持日历拖动。
- 视频日志是 `kind=VIDEO` 的 Action 过滤视图，不建立独立实体。

### 12.2 固定生产 Recipe

P0 只有一条生产 Recipe：

```text
NORMALIZE
→ EDIT
→ QUALITY_CHECK
→ FREEZE_BODY
→ COVER
→ WEB_FORMAT
→ WECHAT_FORMAT
→ REVIEW_READY
```

阶段规则：

- `NORMALIZE` 整理输入格式，不改变正文观点。
- `EDIT` 可以调整结构和语言，必须列出新增、删除和重组。
- `QUALITY_CHECK` 检查事实来源、时效、隐私、夸大、反例和观点偏移。
- 未解决的高风险项阻止 `FREEZE_BODY`。
- `COVER`、`WEB_FORMAT` 和 `WECHAT_FORMAT` 只消费冻结正文。
- 格式化阶段不得修改正文语义；需要实质修改时返回 `EDIT` 并生成新版本。

### 12.3 固定工具组合

| 阶段 | P0 默认实现 | 失败时 |
|---|---|---|
| 内容加工与检查 | 本机 Codex CLI | 重试；人工上传编辑稿或检查结果 |
| 封面策划 | `pyang5166/gbro-cover-design` 固定提交 | 使用固定品牌模板 |
| 封面生成 | 一个已配置的 Image Generator Adapter | 人工上传对应尺寸封面 |
| 公众号排版 | `cyberxiaowan/xiaowan-wechat-layout-skill` 固定提交 | 导出安全基础 HTML 或上传人工 HTML |
| 网站发布 | 现有 `content:gen`、构建和发布脚本 | 导出网站发布包并人工运行现有流程 |
| 公众号草稿 | 正常登录会话中的浏览器辅助 | 下载 HTML、图片和字段清单后人工复制 |

P0 不提供工具安装界面。每个 Stage 依赖稳定的 capability 名称，具体实现由本地配置映射。未来接入 Skill、MCP 或其他 GitHub 工具时，只替换 Adapter，不改变作品状态机。

### 12.4 集中审批

审批页必须同时回答：

1. 原稿说了什么；
2. AI 改了什么；
3. 是否新增事实或改变立场；
4. 当前还有什么风险；
5. 网站最终会是什么样；
6. 公众号最终会是什么样；
7. 两张封面文字是否正确；
8. 批准的是哪个 Artifact 哈希。

审批动作：

- **批准：** 冻结当前版本并允许发布；
- **一句话退回：** 说明需要改变的结果，创建新加工版本；
- **恢复：** 将历史 Artifact 复制为新的候选版本，不改写历史；
- **取消：** 停止当前作品，保留原稿和已有 Artifact。

### 12.5 发布

网站发布：

1. 将已批准 Markdown 和公开资源写入正式内容路径；
2. 生成内容并执行构建；
3. 检查 Git 预期变更集；
4. 发现无关工作区改动时停止，不顺带提交；
5. 推送独立提交；
6. 验证正式 URL、标题、正文特征和资源；
7. 记录 Publication 状态与 URL。

公众号发布：

1. 准备标题、摘要、作者、正文 HTML、正文图片和横版封面；
2. 在正常登录会话中辅助填写；
3. 保存草稿；
4. 停在最终公开确认之前；
5. 若页面变化或登录失效，导出完整公众号包供人工复制。

## 13. 状态模型

### 13.1 用户可见状态

```text
Topic: INBOX → CANDIDATE → SELECTED | ARCHIVED

Work:
DRAFT_READY
→ PROCESSING
→ REVIEW_READY
→ APPROVED
→ PUBLISHING
→ PARTIALLY_PUBLISHED | COMPLETED

辅助状态：NEEDS_INPUT、CHANGES_REQUESTED、FAILED、CANCELLED

Action: OPEN ↔ DONE

Publication:
PENDING → PUBLISHING → PUBLISHED | WAITING_USER | FAILED
```

### 13.2 底层对象映射

| 用户概念 | 现有或新增真相源 | 说明 |
|---|---|---|
| 选题 Topic | Seed | 不创建并行选题表 |
| 问题来源 | Clue | P0 只做手工录入和关联 |
| 已主选项目 | Execution | 仍由人工主选动作产生 |
| 作品 Work | Execution + Submission 聚合 | 前台显示为一条作品时间线 |
| 阶段结果 | 本地 Artifact + manifest | P0 不为每个 Stage 建关系表 |
| 待办与视频 | Action | 通过 kind 区分，不建视频表 |
| 渠道发布 | Publication | 网站和公众号分别一条记录 |
| 公开正文 | `content/log` | 只有批准版本进入正式内容真相源 |

## 14. Artifact 与数据要求

### 14.1 作品目录

```text
var/works/<workId>/
├─ original/       只读原稿和原始附件
├─ stages/         各阶段 Artifact
├─ final/          冻结正文、双封面和平台稿
├─ publish/        发布包、结果与人工接管文件
└─ manifest.json   状态、版本、哈希、工具与运行记录
```

`var/works` 不进入 Git。批准后只有正式 Markdown、公开素材和现有内容生成结果进入 Git。

### 14.2 最小新增数据

| 对象 | 最小字段 |
|---|---|
| Submission | id、executionId、title、status、manifestPath、approvedArtifactHash、createdAt、updatedAt |
| Action | id、title、note、kind、entityType、entityId、status、plannedDate、completedAt、source、createdAt、updatedAt |
| Publication | id、submissionId、channel、artifactHash、status、url、lastError、publishedAt、createdAt、updatedAt |

详细 Stage 日志、工具版本和输入输出哈希保存在 manifest，不在 P0 建立通用 ToolInstallation 与 Stage 关系模型。

## 15. 业务兜底

### 15.1 固定兜底顺序

```text
当前阶段自动重试，最多两次
→ 使用本地配置中已经存在的替代实现
→ 人工完成当前阶段并上传 Artifact
→ 导出完整作品包，离开系统继续工作
```

### 15.2 失败页必须提供

- 失败阶段与可理解原因；
- 最近一个成功 Artifact；
- 重试当前阶段；
- 使用已配置替代实现；
- 下载输入并上传人工结果；
- 恢复历史版本；
- 跳过明确标记为非必要的阶段；
- 导出完整作品包；
- 取消作品。

### 15.3 连续性底线

1. 原稿永久保留；
2. 成功阶段永久保留；
3. 只重做失败阶段；
4. 人工完成后可重新交回后续自动化；
5. 网站和公众号独立成败；
6. 没有 AI 时仍能人工发布；
7. 导出文件不依赖 AdgaiWalker 才能阅读。

## 16. 安全与发布约束

### 16.1 执行边界

- AI 只读取当前 Stage 映射的文件和必要配置。
- 私密原稿不写入命令行参数、Git、公开日志或错误报告。
- Skill 和 Adapter 只能产生 Artifact，不能直接写正式内容路径。
- 发布器只读取批准哈希对应的 Artifact。
- 浏览器辅助只使用用户已有正常登录会话。
- 遇到验证码、重新登录、权限确认或风控提示时交还用户处理。

### 16.2 发布前硬检查

- 原稿存在且哈希未变；
- 核心观点没有未说明改变；
- AI 新增事实有来源或明确标为待核实；
- 没有私密信息泄露；
- Markdown 可以构建；
- 网站资源不存在本地临时路径；
- 公众号 HTML 不含脚本、乱码和失效本地图片；
- 390px 预览没有严重布局错位；
- 双封面中文标题逐字正确；
- 发布 Artifact 哈希等于批准哈希。

## 17. 体验与交互要求

Apple Design 原则在 P0 只服务于可控、清晰和恢复，不扩张成交互工程项目。

### 17.1 即时反馈

- 点击后立即反馈，长任务显示阶段、耗时和最近输出。
- 状态、警告和错误同时使用文字或图标，不只依赖颜色。
- 表单错误靠近对应字段展示。

### 17.2 用户控制

- AI 建议与用户决定在文案和视觉上明确区分。
- Action 勾选、排期、退回和恢复都可逆。
- 运行中的任务可以终止，已成功 Artifact 不丢失。
- 确认对话只用于公开发布、永久删除和其他真正不可逆动作。

### 17.3 P0 交互收缩

- 排期使用日期选择器，不做拖拽日历。
- 状态变化使用短淡入或简单 CSS 过渡，不引入专用弹簧动效库。
- 不为装饰使用大面积模糊、视差或回弹。
- 系统必须支持键盘操作、放大文字、减少动态效果、降低透明度和提高对比度。

## 18. 技术约束

本节记录已存在或直接决定产品可交付性的技术约束，不把技术模块当作产品需求。

| 层 | P0 决策 |
|---|---|
| 包管理 | 继续使用 pnpm 9 workspace 和 Node.js 20+ |
| Admin | 扩展现有 React 19、Vite 6、React Router 7 应用 |
| API | 扩展现有 NestJS 11 API，不拆微服务 |
| 数据 | Prisma 6 + SQLite，本地优先；同步维护 PostgreSQL schema 对齐 |
| 共享契约 | 状态、规则和路由继续放在 `@walker/shared` |
| AI 执行 | NestJS 通过子进程调用本机 Codex CLI，解析 JSONL 并验证结构化结果 |
| Artifact | 使用 `var/works` 本地目录和原子写入 |
| 网站发布 | 继续使用 `content/log`、`content:gen`、构建脚本和 Git → Vercel 流程 |
| 测试 | Vitest、Testing Library 和现有 acceptance scripts |

P0 不引入：

- Redis、外部任务队列和分布式执行；
- 通用 Agent 框架；
- 通用 MCP Host 和工具市场；
- 第二个 AI Provider；
- `@dnd-kit` 和专用 Motion 依赖；
- 新的全局状态框架；
- 云端多用户认证。

工具可替换边界保持为：

```text
业务 Stage
→ capability
→ 本地配置
→ 固定 Adapter
→ 结构化 Artifact
```

## 19. 测试与验收

### 19.1 关键规则测试

- 没有用户动作时 Seed 不能进入 SELECTED。
- AI 创建的 Action 默认 `plannedDate=null`。
- Action 完成和恢复正确写入或清空 `completedAt`。
- 后续阶段不能修改 original 文件。
- 未批准 Submission 不能进入发布。
- Artifact 输出格式错误时不推进 Stage。
- 发布器拒绝批准哈希以外的结果。
- 网站和公众号 Publication 状态互不覆盖。

### 19.2 集成测试

- SQLite 对象与作品 manifest 状态一致。
- Codex JSONL 事件能转换为用户可见进度。
- 进程超时、应用重启和人工终止不污染上一个 Artifact。
- 封面单张失败只重做对应图片。
- 公众号排版不改变冻结正文。
- 网站发布发现无关 Git 修改时停止。
- 人工上传符合格式的 Artifact 后可以继续下一阶段。
- 完整导出包在另一个目录中可以独立打开。

### 19.3 首个纵向验收

一篇真实初稿必须完整通过：

1. 人工主选或确认已有初稿为人工主选；
2. 上传原稿和至少一种附件；
3. 保存核心观点和禁止改变项；
4. 固定 Recipe 完成加工和检查；
5. 生成双封面、网站 Markdown 和公众号 HTML；
6. 在一个审批页完成批准；
7. 网站发布并验证正式 URL；
8. 公众号形成完整草稿或可直接人工复制的发布包；
9. 记录一条真实反馈并转为新 Seed 或 Action；
10. 模拟一个 Stage 失败并完成恢复。

### 19.4 MVP 最终验收

连续三篇真实作品满足第 5.3 节全部指标。只有通过后，才根据第 5.4 节暴露的最大瓶颈决定下一阶段。

## 20. 实施切片

### Slice 1：一篇作品的骨架

范围：轻量选题、Action、创建作品、上传初稿、核心观点、只读 original 和作品时间线。

验收：一个真实选题可以被人工主选，一篇真实初稿可以形成可追踪作品。

### Slice 2：初稿到可审批成品

范围：固定 Recipe、Codex Runner、Artifact、质量检查、双封面、网站稿、公众号稿和集中审批。

验收：一篇真实初稿形成完整可批准成品；一次模拟失败能由人工 Artifact 接管。

### Slice 3：发布与三篇验证

范围：网站发布、公众号草稿辅助、独立 Publication、完整导出、最小反馈和三篇连续验证。

验收：满足第 19.4 节，不以页面数量或模块数量代替业务结果。

## 21. 风险与应对

| 风险 | 会破坏什么 | P0 应对 |
|---|---|---|
| AI 改变作者观点 | 个人品牌和信任 | 独立保存核心观点、展示修改摘要、检测偏移并由作者审批 |
| 固定工具不适合真实作品 | 连续三篇无法复用 | 记录每篇人工接管点；达到推翻条件后再建设工具注册 |
| Codex CLI 版本变化 | 自动流程中断 | 固定已验证版本，封装 Adapter，并用结构契约测试隔离变化 |
| 本机进程或应用中断 | 长任务停止 | 原子保存 Stage、持久化 manifest、从最近成功 Artifact 恢复 |
| 公众号页面变化 | 草稿辅助失败 | 保留完整 HTML、图片、封面和字段清单供人工复制 |
| Git 工作树含用户改动 | 误提交其他内容 | 发布前检查预期变更集，发现无关修改就停止 |
| 过早扩张工具平台 | 延迟第一篇真实作品 | P0 固定 15 项，新增项目必须替换而不能叠加 |

## 22. 后续路线，不属于本 PRD 验收

### P1：按验证瓶颈选择一项

- AI 问题调查与证据管理；
- 选题评分与聚类；
- capability 注册和工具管理；
- 日历拖动与更强排期；
- 已授权平台数据回收；
- 内容拆条和多平台转译。

### P2：平台化

- MCP 管理和远程 Tool Runner；
- 工具安装、版本并存、权限审计和插件市场；
- 多人协作与云端工作区；
- 多平台自动分发；
- 客户、产品和商业化管理。

P1 与 P2 只能由真实使用证据启动，不能因为技术上可实现而提前进入 P0。

## 23. 最终开工判断

本 PRD 可以进入实施计划的前提是：

- 产品目标仍是最快验证初稿到成品闭环；
- P0 保持 15 项，不恢复旧版 60 项范围；
- 工具自由加载只保留技术边界，不建设首期产品界面；
- 第一个开发里程碑是一篇真实作品，不是工具中心或经营看板；
- 三篇验证之前，不新增独立业务模块。

若以上任一前提被推翻，应先重审产品边界，再修改实施计划。
