# C24：验收完整内容更新闭环

任务：C24 验收完整内容更新闭环（前置 C20、C22、C23）
落点：`apps/api/src/content-lifecycle.closed-loop.kernel.integration.test.ts`、`packages/shared/src/public-snapshot.ts`、`apps/api/src/content-release/content-release.service.ts`、`scripts/generate-content.ts`

## 1. 端到端演练：一次完整内容更新闭环

新增 Kernel 集成验收（隔离 SQLite + 临时内容/候选/快照目录 + 假 runner/核验器），单条用例串行跑完并逐步断言：

1. **人工编辑与初稿受控保存**（A02）：`ContentAdminService.save` 经 CAS 写入；三版本快照初始为「正本存在、未发布、未索引」。
2. **Agent 候选生成**（A11）：候选独立落盘，`ContentChange` 为 `PROPOSED`，**正本逐字节不变**。
3. **差异化审批与一次性消费**（A12）：`approve` 绑定 base/candidate/grant 修订；`apply` 原子消费并落盘，正本 hash 变为候选 hash。
4. **实际发布范围预检与稳定清单**（C12）：`preflight` 产出 manifest，`targetHash` 与正本一致。
5. **独立发布批准与准备**（C20 / A02）：产出 `PREPARED` 记录，`publishApproval.binding.action = publish-website`；**保存 ≠ 发布**。
6. **发布阶段推进**（C14）：`release` 触发后进入 `COMMITTING` → `PUSHED`（含 gitCommit）→ `VERIFYING`，退出码 0 绝不提前记 `PUBLISHED`。
7. **线上核验与问答快照同步**（C16/C17/A16）：线上证据（构建期同规则产出的 manifest 条目 hash）与释放记录同口径后，`verify` 得 `PUBLISHED` + `SYNCED`，快照指针切换。
8. **三版本事实终态**：`workingHash`（文件内容）与 `publishedHash`/`indexedHash`（公开投影）各自独立、均可追溯。

## 2. 过程中发现并修复的真实缺陷（P0）

**问题：线上核验在真实链路上永远不可能通过。**

- `ContentRelease.sourceHash` 存的是**正本文件字节的 SHA-256**；
- 线上证据（文章 HTML `<meta name="content-hash">` 与 `public-manifest.json` 条目 hash）是**公开投影哈希**（`projectPublicItems → stableJson`）。
- `verify()` 要求 `verifiedHash === release.sourceHash`，快照同步又要求 `targetEntry.hash === release.sourceHash` → 两个命名空间不同，**生产环境必然永不通过**。

**实测证据（真实仓库数据，vibe0s）**：

| 身份 | 值 |
|---|---|
| 正本文件 SHA-256 | `db16f5869f0446982925e8e9b14e507c791cd065ed9d644a3e34a0b874d1cc62` |
| 线上 HTML content-hash / manifest 条目 hash | `25885fc277f91716eef205c56798ef8834c76bcd156a5da0b483ce74d6ce097e` |

两者不等，且构建产物自洽（manifest 自校验、HTML 与 manifest 一致）——说明**构建侧正确，API 侧用了错的身份**。

**此前为何没被发现**：C17 的测试用 `makeReleaseAtVerifying` 直接以 manifest 条目 hash 构造 release 夹具，绕过了 `prepareRelease`，于是「C12/C14 的文件哈希世界」与「C16/C17 的公开投影世界」从未真正接上。C24 把两半串起来后，缺陷立即暴露。

**修复（单一真相源，不写兼容层）**：

1. `packages/shared/src/public-snapshot.ts` 新增并导出 `toPublicSnapshotSource`、`publicItemHash`、`normalizeLegacyBody`：正本 frontmatter+body → 公开快照来源的唯一映射，以及单篇公开条目 hash 的唯一口径。
2. `prepareRelease` 改为：`sourceHash = publicItemHash(...)`（公开投影身份，与线上证据同口径）；`baseHash` 同为公开命名空间（被替换的线上版本）。**文件版本仍由 `changeId → change.appliedHash` 追溯**，因此不需要新增列或迁移。
3. `scripts/generate-content.ts` 删掉本地重复的 `normalizeLegacyMdx`/`tagAttribute`（约 50 行），改调用共享 `normalizeLegacyBody` —— 消除「两处各写一份映射」的漂移源。
4. 恢复并保留站主**人工发布**路径（人工保存按 C05 语义不产生候选），为其建立并列受控记录；显式传入 `changeId` 时严格校验「已应用且与当前文件版本一致」。
