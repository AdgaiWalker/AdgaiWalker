# C11：清点并封闭内容写入旁路

## 实施结果

### 1. 全仓内容正本写入清单与收敛

通过全局搜索，对全仓所有正本文件写入（`content/log`）、候选持久化、状态流转与发布触发调用点进行了全面清点，结果如下：

| 调用源 | 原实现方式 | C11 状态与收敛方案 | 鉴权与审计保障 |
|---|---|---|---|
| `ContentAdminController.save` (`PUT /admin/content/:slug`) | 原直接写文件仓储并触发子进程索引生成 | **已收敛**：C05 委托给 `ContentMutationService.saveManual` | `AdminTokenMiddleware` 保护；固定站主 actor；必须携带 `expectedHash` CAS；写前记录 intent audit，写后记录 completed/conflict audit；移除保存后自动重建公共索引 |
| `ContentChangeController.apply` (`POST /ops/content-changes/:id/apply`) | 原无独立候选应用出口 | **已收敛**：C09 委托给 `ContentMutationService.apply` | `AdminTokenMiddleware` 保护；复检 L2 授权有效性/撤销状态/修订版本及原文基线冲突；单个 SQLite 事务原子消费审批 (`beginApply`) 并写 intent audit；CAS 写文件；终态记为 `APPLIED` 并写结果 audit；绝不自动包含发布 |
| `PublicationService.publishWebsite` (`POST /works/:id/publish/website`) | 原直接调用 `files.save` 绕过审计日志 | **已封闭并收敛**：C11 改为委托 `ContentMutationService.saveManual` | 注入 `CONTENT_MUTATION_SERVICE`；执行前通过 `existing?.hash` 传递 `expectedHash` 进行 CAS；产生完整的 `content.manual-save.intent` 与 `content.manual-save.completed` 审计；保存状态如实标记为 `PREPARED` |
| `FsContentFileRepository.save` | 底层文件落地操作 | **唯一落盘出口**：按 slug 进程对象锁串行化、CAS 对比、同目录唯一临时文件写入与原子 `fs.rename` 替换 | 拒绝路径穿越；仅允许由受控的 `ContentMutationService` 调用，全仓无任何其他业务服务直接调用 |
| Agent MCP / 技能工具 | 只读工具集 | **无写能力**：Agent 仅持有 9 项只读工具（`search_judgment` 等），运行 profile 强制锁定为 `READ_ONLY_PROFILE`，不存在任何正本写工具 | `origin: 'public'` 强制 `grantId: null`，绝无写入正本权限 |
| 访客及公开 API | 公开端点 | **白名单硬隔离**：公开路由仅放行 13 条精确匹配端点，均无内容或状态写权限 | `SameOriginMiddleware` 校验 Origin/Referer；伪造管理员请求直接 401 拦截，无法提权 |

### 2. 旁路封闭验证

- 检查 `CONTENT_FILE_REPOSITORY.save` 的调用方：除核心受控服务 `ContentMutationService` 外，原旧工作站 `PublicationService` 的直接调用已被改写为委托 `saveManual`，全仓正本写入口彻底归口唯一受审计出口。
- 清单核查完毕，无未处理可达写旁路。
