# C18：实现结果不明的发布核对

## 实施结果

- **状态机流转支持核对确证**：
  - 更新 `@walker/shared` 的 `CONTENT_RELEASE_TRANSITIONS`，允许 `UNKNOWN` 状态在事实核对时合法流转到 `VERIFYING`、`FAILED` 或在持有有效验证证据（`expectedHash === verifiedHash`）时流转到 `PUBLISHED`。
  - 维护非核对场景不可跳阶段的基本纪律（如 `PREPARED -> PUBLISHED` 仍严格拒绝）。
- **Git 事实检测能力扩展（`GitStatusPort` 与 `NodeGitStatusRepository`）**：
  - 扩展 `GitStatusPort.hasCommit(commit: string)`，使用 Git 原生无 shell 命令 `git cat-file -e <commit>^{commit}` 进行 O(1) 提交对象存在性验证，确证已落盘提交事实。
- **结果不明发布核对用例（`ContentReleaseService.reconcile`）**：
  - **线上确证优先**：对处于 `UNKNOWN`、`COMMITTING`、`PUSHED` 或 `VERIFYING` 的发布，优先调用 `websiteVerifier.verify`。若线上已确认目标 hash，直接将阶段确证为 `PUBLISHED` 并自动触发 C17 问答快照同步，返回 `resolved: true, nextAction: 'none'`。
  - **Git 事实确证与严防二次提交**：
    - 若已有提交记录（`gitCommit`）或 Git 历史已确证该提交存在，证明内容已提交并推送远端，阶段转为/维持为 `VERIFYING`，`nextAction: 'wait-deployment'`；
    - **核心红线**：绝不再次触发发布脚本或生成多余提交，防止 Git 历史污染。
  - **未发生提交的中断保护**：
    - 若在 `COMMITTING` 阶段中断且工作区目标文件仍处于脏状态（未提交），判定为提交未发生即中断，安全将阶段置为 `FAILED`（`errorCode: 'commit-interrupted'`），`nextAction: 'none'`，允许用户重新发起发布。
  - **保留 UNKNOWN 与给出指引**：
    - 若线上不可达且 Git 状态不可用（如网络断开、远端不可连），保持 `UNKNOWN`，`nextAction: 'check-git-remote'`，绝不伪造结果。
- **HTTP 控制器接入**：
  - 在 `ContentReleaseController` 暴露 `POST /admin/content/release/:id/reconcile`。
