# O02：实现到期扫描与恢复补检

前置：O01、R05。落点：OperationsService 定时扫描。
验收：K2；跨日/重复扫描/进程重启不丢不重复，不调用模型、不发外部通知；已有提醒无需新建 Agent 进程。

## 1. 实现

新增 [`apps/api/src/reminder/reminder-scan.service.ts`](../../apps/api/src/reminder/reminder-scan.service.ts)，沿用仓库既有调度约定（对照 `AgentExecutionService`）：

- `REMINDER_SCAN_INTERVAL_MS = 5 * 60 * 1000`：每 **5 分钟**一轮（TECH-DESIGN §12.4 原文口径）。
- `scanOnce(now)`：唯一扫描入口，生产定时器、启动补检与测试**走同一个方法**（不给测试另写一条路径）。
- `startScheduler()`：起计时器；幂等（已启动则直接返回），`timer.unref?.()` 保证不拖住进程退出；`onModuleDestroy` 干净清理。
- 单轮限流：单批 200 条（`REMINDER_SCAN_BATCH_LIMIT`）、至多 20 轮（`SCAN_PASS_LIMIT`），保证单轮时长可控。
- **防重入**：`scanning` 标志，上一轮未完成则本轮直接返回零计数。
- **fail-closed**：恢复门挂起（`isRestoreGatePending`）或库不可写时不扫描。
- **结果如实计数**：`{ scannedAt, created, deduped, skipped }`，已存在只计 `deduped`。

启动接线（[`main.ts`](../../apps/api/src/main.ts)）：恢复门清除、`WALKER_STARTUP_RECONCILIATION=0` 之后先 `scanOnce()` 补检、再 `startScheduler()`，与既有保留期清理、会话删除恢复、执行调度器并列。

去重不靠应用层判断：O01 建的 `ReminderOccurrence.dedupeKey` 唯一索引（键不含扫描时间）是唯一保证；扫描只负责「反复敲门」。

## 2. 验证

### 2.1 K2 Kernel 集成测试（`apps/api/src/reminder/reminder-scan.kernel.integration.test.ts`，10 项）

| 用例 | 断言要点 |
|---|---|
| 只领取到期且未完成事项 | 已到期→1 条；未到期→0 条；已到期但已完成→0 条 |
| **重复扫描不重复产生** | 连续三轮扫描后恒为 **1 条**；第二、三轮如实计入 `deduped` |
| **跨日补扫 + 进程重启** | 关闭并重建整套模块（新服务实例、同一库）后再扫：仍为 1 条且计入 `deduped`；**不丢不重复** |
| **延后不触发旧到期** | 旧到期产生 1 条 → 改期到 2026-10-20（`dueAt` 原子重算为 `2026-10-19T16:00:00.000Z`）→ 在旧到期之后、新到期之前扫描**仍为 1 条** → 新到期后才变 2 条 |
| 未排期/已完成 | 均不产生记录 |
| 计数一致 | 首轮 `created > 0`；复扫 `created === 0` 且 `deduped > 0`；库内恒 1 条 |
| 并发防重入 | 三路并发 `scanOnce` 后仅 1 条记录 |
| 计时器生命周期 | 重复启动不叠加（只有一个计时器）、`onModuleDestroy` 后归零、停止后再启动幂等 |
| **不调模型/不发外部通知** | 监视 `globalThis.fetch`：**零调用**；比对 `ExecutionRun` 行数：**一字未增**（没有模型进程被新建）；唯一副作用是本地 1 条发生记录 |
| **恢复门 fail-closed** | 写入 `restore.pending` 后扫描计数全 0、无记录；清除后恢复正常并产生 1 条 |

> 说明：最初尝试直接改写 `node:child_process` 的 ESM 命名空间导出以拦截 `spawn`，Vite/ESM 下不可重定义。改用**更强的库级证据**：模型只能经统一执行服务跑，因此「`ExecutionRun` 行数不增」比拦截函数更直接地证明没有新建 Agent 进程。
