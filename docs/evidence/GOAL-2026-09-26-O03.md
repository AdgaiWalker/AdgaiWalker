# O03：实现提醒完成、延后与忽略

前置：O02。落点：现有 Action service/controller。
验收：K2；连续延后不触发旧到期提醒，重复完成无额外副作用；未实现重复规则明确拒绝。

## 1. 实现

### 1.1 处置语义（三种动作，各自一个主要行为）

| 动作 | Action 变化 | 发生记录 | 要点 |
|---|---|---|---|
| `complete` 完成 | `status=DONE`、`completedAt=now`、`dueAt=null` | `DONE` | 保留 `plannedDate` 作历史事实；清 `dueAt` 使完成项不再被扫描领取 |
| `snooze` 延后 | `plannedDate/dueAt/timezone` **原子重算** | `SNOOZED` | 旧到期随之失效（`dueAt` 无残留），这是「连续延后不触发旧提醒」的前提 |
| `ignore` 忽略 | 仅 `dueAt=null`，**`status` 保持 `OPEN`** | `IGNORED`（可带 `reason`） | 忽略 = 撤下这次到期，不等于事项结束 |

### 1.2 原子性是本次的核心设计

新增专用端口 [`reminder-disposition.port.ts`](../../apps/api/src/ports/reminder-disposition.port.ts) + 适配器 [`prisma-reminder-disposition.repository.ts`](../../apps/api/src/adapters/prisma-reminder-disposition.repository.ts)。

**为什么不塞进既有 `OperationsJournalPort`**：既有事务视图只暴露 `runs/grants/appendAudit`，不含 `Action` 与 `ReminderOccurrence`。处置必须让「发生记录结果 + Action 更新 + 审计」**同事务提交**，否则中途失败会留下「提醒已标记处理、事项却仍指向旧到期」的半截状态——用户看到已忽略，扫描却仍会把它捡起来。

### 1.3 幂等与拒绝

- **`requestKey` 幂等**：以审计行（`targetType=action` + `action=reminder.disposition` + `requestId=requestKey`）为幂等依据，**不额外建表**——审计已是原子提交的既有事实来源。重放返回 `replayed: true` 且不写第二行审计。
- **未实现重复规则明确拒绝**：`repeat` 非 `none` 时返回 **501**，覆盖三处入口（处置、`POST /actions`、`PATCH /actions/:id`）。字段已预留但首期只做单次；**绝不静默丢弃或降级**——否则站主以为设了每周提醒，实际只响一次。
- **审计读取按 action 过滤**：`auditRecord` 是通用表，`listDispositions` 只回处置条目，不把将来同 `targetId` 的其它审计混进来；审计常量在端口单点定义，写入与读取共用同一份。

## 2. 验证

### 2.1 K2 Kernel 集成测试（`reminder-disposition.kernel.integration.test.ts`，9 项）

1. 完成：事项转 `DONE`、`completedAt` 落值、`dueAt` 清空、发生记录 `DONE`、审计留痕。
2. **重复完成无额外副作用**：同 `requestKey` 重放 → `replayed: true`、同 `occurrenceId`，审计与发生记录都仍是 1 条。
3. **连续延后不触发旧到期**：`2026-09-20` → 延后 `2026-10-10`（`dueAt` 变 `2026-10-09T16:00Z`）→ 再延后 `2026-11-05`（`2026-11-04T16:00Z`）；在旧到期之后、新到期之前**连扫两轮**仍只有 1 条历史记录；新到期到来后才出现第 2 条。
4. 忽略：发生记录 `IGNORED` 且带原因，事项**仍 `OPEN`**、`dueAt` 清空、不再被扫描领取。
5. **未实现重复规则明确拒绝**：`repeat: 'weekly'` 抛错；`repeat: 'none'` 正常通过。
6. **创建/更新入口同样拒绝**：`create`/`update` 带 `repeat` 抛错，`none` 通过——不在入口静默丢字段。
7. 参数校验：缺 `actionId`/`requestKey`、非法处置、延后缺日期、非法日期、事项不存在分别被拒。
8. **事务原子性（故障注入）**：在事务体内注入失败后，事项状态、`dueAt`、发生记录结果、审计**四者一起回滚**，无半截状态；恢复后同一 `requestKey` 可正常完成（失败请求键未被消费）。
9. **不调模型、不发外部通知**：`fetch` 零调用、`ExecutionRun` 行数一字未增。

### 2.2 HTTP 出口集成测试（`reminder-disposition-http.integration.test.ts`，3 项）

真实 `AppModule`：匿名 401；完成处置 201 且重放 `replayed: true`、处置历史仅 1 条；延后 `dueAt` 为 `2026-10-09T16:00:00.000Z`、忽略 201、`repeat: 'weekly'` 返回 **501**。
