# V24：首个文章位置与日志闭环

## 目标与结论

沿一篇文章的位置走完公开问答、成员切换、访客历史、后台回看、受控导出、删除和旧备份恢复。V24 已完成本地验收，未部署。所有 API 端到端数据使用隔离 SQLite；模型由可控 Runtime fixture 返回，不发送外网请求。

测试中的部署成员是两个不同 Agent 修订。服务端有效 readiness fixture 只供测试验证允许路径，不修改当前本机探针配置。当前 `apps/api/.env` 未配置 `WALKER_RUNTIME_PROBE_REPORT`，真实公共位置仍由 V23 gate 阻断。

## Kernel 集成路径

新增 `apps/api/src/assistant/public-journey.kernel.integration.test.ts`，使用真实 `AppModule`、SQLite、部署/权限/对话/导出/删除仓储和假 Runtime：

1. 创建两个只读修订，为两者建立三类 release-test 证据；提供已核验文章快照及完整的隔离探针 fixture，启用 `post-detail` 位置。
2. 同一访客先由默认成员回答，再显式切换到第二成员回答。两轮复用同一业务会话，修订级 SDK session 输入互相隔离；事件与引用只属于当前访客和快照。
3. 访客刷新历史后仍看到两轮和各自成员修订；其他访客没有历史。Records 服务端筛选、详情中逐轮消息/成员/交互可回看；公开 ExecutionRun 为 `origin=public`、`grantId=null`。
4. 管理端创建并下载冻结范围 JSON，包含两轮问题和回答。删除完成后，管理详情变 404、公开历史清空、job 撤销、本机文件消失。
5. 在删除前用 SQLite `VACUUM INTO` 创建快照；删除后复制到另一临时 `.test.db`，重放同一 deletion manifest，再运行正式清理用例。旧快照先能读到四条消息；清理后会话/消息数为零、tombstone 为 `completed`、manifest replay 完成。

这条测试刻意覆盖跨层约束，而不是只核对 API 的成功状态：公开运行没有后台授权、访客归属不串、引用不超出当前快照、成员切换保持业务时间线但不共用模型 session、导出不绕过筛选快照、删除的文件副本和旧 SQLite 备份都不能复活对话。
