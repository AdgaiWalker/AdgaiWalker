# C04：内容写入意图与崩溃恢复

## 实施结果

- 新增 `ContentMutationService.apply/reconcile` 并注册到 Kernel。apply 只接受与已批准 `candidateHash` 完全一致的正文 bytes；当前内部调用方直接提供字符串，`candidateRef` 读取留给 C07，未新增 HTTP 写端点。
- `ContentChangeRepository.beginApply` 使用一个 Prisma SQLite 事务把 `APPROVED → APPLYING` 与 `AuditRecord(content.apply.intent)` 一起提交，固定 `baseHash`/`candidateHash` 和 requestId。重复调用已经 APPLYING/APPLIED 的候选不会重写 intent audit。
- 文件写仍由 C03 `ContentFileRepository.save(slug, candidateRaw, baseHash)` 单独完成；文件系统与数据库不宣称跨资源原子。写完后 `finishApply` 再用另一个事务提交状态、`appliedHash` 和结果 audit。
- `reconcile` 读取当前文件 hash：等于候选 hash 时只补数据库完成事实，不再次写文件；仍等于 base hash 时对相同且已批准的正文安全重试 CAS；其他 hash 标记 CONFLICT 并保留当前正文。文件读不可用或恢复调用失败时保留 APPLYING，后续可再次核对。
- `reconcile` 是可调用的恢复用例；本次没有新增 API、启动期扫描或后台自动任务。候选原文现在由可信内部调用方传入并校验 hash，C07/C09 再接 opaque candidateRef 的读取和恢复触发。
- 意图和结果均通过既有 `AuditRecord` 留 before/after hash；没有新增 SQLite 表或迁移。

## 验收边界

- C04 的 apply/reconcile 是内部服务，没有管理 HTTP 候选接口。调用方目前传入候选原文，服务校验 SHA-256；C07 接入从 opaque `candidateRef` 读取不可变候选文件。
- 原有 `/admin/content` 人工保存仍走既有 service，虽然 C03 已要求 expectedHash，但它尚未通过 `ContentMutationService` 记录 intent audit，保存后仍会触发 `content:gen`；C05 负责人工保存受控出口和移除索引副作用。
- 文件系统写入与 SQLite 状态/审计分开提交。退出窗口由 APPLYING + 磁盘 hash 恢复，不宣称分布式/跨资源原子性。测试只使用 API 隔离 SQLite 和系统临时内容目录；没有修改 `content/log`、调用模型、增加 schema 或部署。
