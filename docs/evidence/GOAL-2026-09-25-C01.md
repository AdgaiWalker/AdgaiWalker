# C01：内容候选、审批与发布合同

## PRD 必要性判断

- **Recommendation**：复用现有 PRD，不另起 PRD；本项是 shared 合同和技术设计任务。
- **Reason**：PRD §4.2 已规定候选与原文分离、保存不等于上线；§5.3 已规定审批绑定动作/对象版本、版本变化后失效、执行前重查授权。C01 将这些行为变成共享的可检查合同，没有增加独立用户旅程。
- **User-visible behavior change**：本地契约/状态验证；不增加数据库迁移或 HTTP 写入口。
- **Scope alignment needed**：新候选与新发布生命周期有独立模型，旧工作站 `Submission/Publication` 保留，接入留 C21。
- **Acceptance needed**：是；审批绑定字段变更须失效，候选应用状态不能冒充网页发布，发布必须过 hash 核验。
- **If not PRD, where it belongs**：shared 合同、技术方案和本验收记录。

## 目标合同

- `ContentChange` 是候选应用事实，动作固定 `apply-candidate`。`APPLIED` 代表工作区内容文件完成 CAS 写入，不代表网页已发布或问答索引已更新。
- `ContentApprovalBinding` 固定 `{action,target,baseHash,candidateHash,grantId,grantRevision}`。apply 的 `baseHash` 是当时工作区正文，publish 的 `baseHash` 是当前已核验网页版本、`candidateHash` 等于 release sourceHash。shared 以固定字段顺序序列化，未知字段、无效 hash/目标/授权修订和空操作都会被拒；API 对规范字节计算 SHA-256。任一绑定字段变化，原批准不再匹配。
- `apply-candidate` 与 `publish-website` 分别批准。`ContentRelease.stage` 记录 `PREPARED → COMMITTING → PUSHED → VERIFYING → PUBLISHED`；只能从 `VERIFYING` 完成，且线上验证 hash 必须和批准的 source hash 相同。
- `assistantIndexState` 独立记录问答索引同步。`ContentVersionSnapshot` 分别呈现 `workingHash`、`publishedHash`、`indexedHash`；三者不同可以解释，不合并成一个状态。
- `ContentApproval` 是一次性不可变值合同，附着到相应 ContentChange/ContentRelease；不建通用审批中心。C02 再按这份合同增加 SQLite 持久化。

### 2. Config Fields

无。以上都是不可变业务版本/副作用/恢复事实，不是可调参数；不放进配置 JSON。

### 3. Runtime Fields

- `workingHash`：读取当前 `content/log/<slug>` UTF-8 正文并计算 hash | source: `ContentFileRepository` | computed: 列表/详情和 CAS 前。
- `publishedHash`：读取最近一次线上 manifest 中与该 slug 对应、且核验成功的正文 hash | source: `ContentRelease`/远端 manifest | computed: 后台版本读模型。
- `indexedHash`：读取当前活动公开快照的 slug 正文 hash | source: `PublicSnapshotRepository` 活动指针 | computed: 后台版本读模型。
- `versionsInSync`：比较三个 hash，不单独持久化 | source: 上述三个权威来源 | computed: 页面响应时。

### 5. Change List

- **Renames**: none；不把 `Submission.approvedArtifactHash` 或 `Publication.artifactHash` 改名冒充新内容合同。
- **New fields/contracts**: shared `ContentChange`、`ContentApprovalBinding/ContentApproval`、`ContentRelease`、`ContentVersionSnapshot`；C01 不做 schema migration。
- **Removals**: none。
- **Moves**: 不建独立审批表；审批绑定/hash/消费事实存在其所属 ContentChange 或 ContentRelease。
- **API gaps**: C01 只有共享合同与纯函数；候选/发布持久化在 C02，端点/执行在 C08–C20。

### 6. Design Decisions

| Decision | Reasoning |
|---|---|
| `candidateRef` / `manifestRef` 都是 opaque ID | 受控 adapter 推导路径，不给请求体或 UI 传服务端文件路径 |
| apply 与 website publish 用不同 `ContentApprovalAction` | 授权写候选不会自动开放发布；重复消费用父记录状态 CAS 完成，不建通用审批中心 |
| `ContentChange` 没有 `PUBLISHED` 状态 | 修改完成和网页上线是两个可独立失败的副作用 |
| 网页 release 与 Q&A index 分别记录 | 部署后索引切换可以失败；需要能如实展示网页 hash 已更新、indexedHash 仍旧 |
| `workingHash/publishedHash/indexedHash` 是读投影 | 它们来自当前文件、线上 manifest、活动 snapshot，存一份“总版本”会丢失真相源差异 |

## Hai TDD

### Target Behavior

共享合同严格绑定一次内容/发布批准；未核验远端正文 hash 时不能将发布状态变成 `PUBLISHED`；编辑、网页与问答索引版本各自表达。

### RED

- **Test added**: `packages/shared/src/content-change.test.ts`。
- **Behavior asserted**: 所有 binding 维度变更失效；SHA-256/hash 值域严格；`PUBLISHED` 不属于 ContentChange，发布不能跳过 `VERIFYING`；index status 值域明确。
- **Command**: `pnpm --filter @walker/shared exec vitest run src/content-change.test.ts`。
- **Observed failure**: 初次运行缺少合同导出；补第一版后，未知 `force` 字段仍被批准比较忽略，且没有 ContentChange 状态转移 helper；索引状态 guard 缺失时再次失败。后续反例还发现 `VERIFYING → PUBLISHED` 可以不提供远端 hash 证明。Release 类型样例最初没有 publish baseHash，TypeScript 编译反例要求补回这条版本绑定。
- **Failure is correct because**: 未知字段被忽略会让客户端静默改变批准语义；未核验 hash 就标发布成功会把脚本成功冒充线上事实；publish 还必须绑定当前线上 baseHash，避免并发期间基线被换。

### GREEN

- **Minimal implementation**: 新增 `packages/shared/src/content-change.ts` 和 barrel export，提供严格目标/hash/binding 检查、固定序列化 key、ContentChange 与 ContentRelease 状态迁移、仅在 `VERIFYING` 且远端 hash 等于批准 sourceHash 时允许转 PUBLISHED、publish 批准绑定线上 baseHash、独立索引状态与三 hash 读投影类型。
- **Command**: `pnpm --filter @walker/shared exec vitest run src/content-change.test.ts`；`pnpm --filter @walker/shared exec tsc --noEmit --target ES2022 --module CommonJS --moduleResolution node --strict --skipLibCheck src/content-change.test.ts`；`pnpm --filter @walker/shared typecheck`。

## 验收边界

- 无 Prisma schema/migration、候选仓储、内容写入端点或发布服务改动；这是 C01 类型与合同定义。旧 `Submission/Publication` 原样保留，后续 C02/C21 分阶段实现。

- 没有写入 `content/log` 或真实生产数据，未部署。
