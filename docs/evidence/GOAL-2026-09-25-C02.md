# C02：内容候选与发布持久模型

## 实施结果

- 新增 SQLite 迁移 `20260925160000_content_change_release`，建立 `ContentChange`、`ContentRelease` 两表。包含每表唯一 `requestKey`、目标/状态时间索引，以及 `ContentRelease.changeId` 到 `ContentChange` 的 `RESTRICT` 外键。
- 候选行保存 `apply-candidate`、slug、base/candidate hash、不透明候选引用、可空来源 run、状态、批准 ID/binding hash/grant ID 与 revision/批准者和时间、应用后 hash。
- 发布行保存 `publish-website`、候选关联、已核验网页 base hash、候选 source hash、独立发布批准快照、PREPARED 阶段、独立 assistant index 状态、manifest/commit/snapshot/核验字段、错误码和请求键。候选应用与网页发布仍是不同父记录状态；未引入通用 Approval 表。
- Kernel 注册 `CONTENT_CHANGE_REPOSITORY` 与 `CONTENT_RELEASE_REPOSITORY`。候选支持幂等创建、按 ID/requestKey 查询、批准快照写入和重启后读取；发布支持幂等创建、按 ID/requestKey 查询及按 changeId 稳定排序列表。
- 同一请求键携带不同候选/release 事实返回 `idempotency-conflict`；回放相同事实返回已有记录。审批只允许 `PROPOSED → APPROVED`，验证严格字段、规范 binding、SHA-256、授权 revision 和 ISO 时间；相同审批重试返回原批准，替换批准冲突。消费事实从候选状态推导。
- 网页 release 只接受 `APPLIED` 候选，且 target、candidateHash 与 appliedHash 均必须匹配 release sourceHash。其 publish approval 必须绑定当前网页 baseHash、候选 sourceHash 和 publish grant 修订。新 release 固定为 `PREPARED` / `PENDING`，manifest 与远端核验事实初始为空。
- 旧 `Submission` / `Publication` schema 与语义保持独立。迁移验收在现有 SQLite 快照中 seed 旧 Submission/Publication，再 baseline 并逐字段确认旧值仍在。

## 行为边界

- 本次只新增数据库模型和 Kernel repository provider；没有新增 HTTP 写端点，也没有接入文件写入、Git、线上发布、公共模型请求或生产部署。
- Release 集成测试将候选状态直接置为 `APPLIED`，只验证 repository 对已应用事实的约束；真正的 CAS 文件保存与状态恢复由 C03/C04 承接，发布阶段推进与远端验证由后续 C14–C17 承接。
- working/published/indexed hash 是不同来源的读投影；C02 没有增加冗余“总版本”字段或新 snapshot 表。
