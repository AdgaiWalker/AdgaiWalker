# G03：完成目标机器资源和并发验收

前置：R21、C19、G02。落点：目标环境探针报告/运行配置。
动作：按默认单模型槽跑公共与后台排队、终止、恢复；验证内存余量、日志/磁盘上限、维护构建流程。
验收：K5；一个活跃模型运行、无孤儿进程、至少512MB目标可用余量或记录不满足并降级/阻止该能力上线；不偷偷扩机器或双槽。

## 1. 并发与资源语义验收（`resource-concurrency.g03.kernel.integration.test.ts`，6 项）

| 验收点 | 结果 |
|---|---|
| **单槽纪律** | 第一条运行 RUNNING 后第二条保持 QUEUED（runtime.start 恰好一次）；槽释放后第二条才被领取；`MODEL_SLOT_LIMIT=1` 阈值固定 |
| **公共排队上限** | 占槽后塞满 `PUBLIC_QUEUE_LIMIT` 条公共排队，第 N+1 条被如实降级（reason 含「已满」），不假装排队成功 |
| **终止语义** | RUNNING 停止走 STOPPING→CANCELLED；`runtime.close` 有真实调用与退出证据；槽立即释放（下一条可领取） |
| **恢复语义** | 遗留 RUNNING（租约丢失）被标记 isolated（UNKNOWN）→ 进程退出被证明后 released（FAILED + lease-lost）；UNKNOWN 仍在占用集合 |
| **资源门禁** | readiness 新增 `resourceHeadroom` 门：真实内存不足 512MB → **阻止该能力上线**（blocked），满足 → ready；状态与真实内存严格一致 |
| **无孤儿进程** | 全部运行收敛终态后占用槽位数为 0 |

## 2. 新增内存余量门禁（落点：`resource-gate.ts` + readiness + 运维配置）

### 2.1 shared 纯函数（单一真相源）

- `DEFAULT_MIN_FREE_MEMORY_MB = 512`（目标机器 2C2G 的要求，不偷偷放宽）；
- `memoryHeadroomOk(freeBytes, minBytes)`：不足时返回如实说明（含具体 MB 数），**阻止而非降门槛**；
- `resolveMinFreeMemoryMb(env)`：允许运维经 `WALKER_MEMORY_HEADROOM_MB` 显式覆盖（默认 512；显式 0 解除；非法值回落默认）。

### 2.2 readiness 集成

`PublicReadinessService` 新增 `resourceHeadroom` 门（读真实 `os.freemem()`）：不满足 → `blocked` → **`canEnable=false`，该能力不得上线**。管理端 `PublicReadinessPanel` 同步增加「目标机器内存余量」标签。

### 2.3 设计决策：门禁放 readiness 而非 dispatch 热路径

第一版把门禁放进了 `dispatchOnce`（每次领取前检查）。全量回归立即否决：**28 个既有测试失败**——开发机跑测试矩阵时内存常态低于 512MB，门禁把所有执行测试的模型启动全部阻断。这暴露了两个问题：① 开发/CI 机器的余量不代表 2C2G 目标盒子；② 验收条款的语义是「**记录不满足并降级/阻止该能力上线**」——这是**上线门**，不是运行时每次调用的热路径检查。

最终设计：门禁在 **readiness（上线门）** 上执行，配合运维 env 覆盖；测试矩阵在 vitest 配置里显式 `WALKER_MEMORY_HEADROOM_MB=0`（运维配置路径）。G03 专项测试会临时恢复默认 512 验证真实阻断行为。

### 2.4 实测注记（诚实记录）

本开发机当前 `os.freemem()` 实测仅 64–100MB——门禁在真实环境里**确实会阻断**。这本身是门禁正确性的现场证据：不满足即 blocked，绝不静默放行。目标盒子的实际余量在 G07 部署时实测。

## 3. 运行配置

- vitest 配置显式 `WALKER_MEMORY_HEADROOM_MB=0`（附注释说明理由：测试机余量不代表目标盒子）；
- 生产不设置该变量 → 默认 512MB 生效。
