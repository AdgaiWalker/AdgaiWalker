# O01：增加提醒发生记录与复盘数据

前置：R02。落点：Action 增量、ReminderOccurrence、ReviewEntry migration/repository。
验收：K2/K6；旧 Action 保留，重复 occurrence 受唯一键约束，日期转 UTC 可还原站点时区。

## 1. 实现

### 1.1 单一时间规则（`packages/shared/src/reminder.ts`）

- `DEFAULT_SITE_TIMEZONE = 'Asia/Shanghai'`；仅设日期的事项按站点时区**当日 00:00** 到期。
- `resolveActionDue({ plannedDate, timezone })` → `{ dueAt, timezone, source }`。换算用 `Intl.DateTimeFormat` 完成（含跨夏令时的二次校正），**不引入时区数据库依赖，也不在别处再写一遍偏移算法**。
- `utcToZonedDate(instant, tz)` 反向还原站点本地日期，保证「日期 → UTC → 日期」无损。
- `reminderOccurrenceKey({ actionId, dueAt, timezone })` = `actionId@dueAt@timezone`：**键刻意不含扫描时间**，否则重复扫描会绕过唯一约束。
- `normalizeReviewWindow` 规范观察窗口（两端有序）；`REMINDER_OUTCOMES`、`REVIEW_EVIDENCE_STATES` 词表。

**关键设计修正（开发中由测试暴露）**：初版对「未排期」的事项返回默认时区，会让 `timezone` 看起来已按时区排期。已改为 **未排期 → timezone 也是 null**：没有瞬时就没有「生成它的时区」。

### 1.2 持久层

- `Action` 增量：`dueAt DateTime?`、`timezone String?`（**可空**，旧行保持 NULL 不反推）+ `@@index([dueAt, status])`。
- 新表 `ReminderOccurrence`：`dedupeKey` **唯一索引**、`outcome`（PENDING/DONE/SNOOZED/IGNORED）、`reason`、`notifiedAt`、`resolvedAt`；外键指向 Action，`onDelete: Cascade`。
- 新表 `ReviewEntry`：`actionId`、`releaseId?`（关联已核验发布版本）、`didWhat`、`observed?`、`windowStart?`/`windowEnd?`、`nextAttempt?`、`evidenceState`（默认 UNKNOWN）、`evidenceNote?`、`createdBy`、`requestKey` **唯一**。
- 迁移 `20260926100000_reminder_review`。
- 仓储：`PrismaReminderOccurrenceRepository`（`createOnce` 撞 P2002 时返回既有记录，`created=false`）、`PrismaReviewEntryRepository`（同 requestKey 幂等）。

### 1.3 用例与接口

- `ReminderService`：`recordDueOccurrence`（幂等）、`listOccurrences`、`resolveDue`、`createReview`（幂等 + 窗口/证据校验）、`listReviews`、`getReview`。
- `ReminderController`：`POST /ops/reminders/resolve-due`、`GET /ops/actions/:id/occurrences`、`POST|GET /ops/reviews`、`GET /ops/reviews/:id`。**默认管理鉴权，未加入公开白名单**。
- `ActionService`：创建与改期时经共享规则推导 `dueAt`/`timezone`；改期**原子重算**（旧 `dueAt` 不残留），这是 O03「连续延后不触发旧提醒」的前提。
- 契约回写：[docs/api/README.md](../api/README.md)。

## 2. 验证

### 2.1 K2 单元测试（`packages/shared/src/reminder.test.ts`，10 项）

- 站点时区当日 00:00 到期：`2026-09-26` → `2026-09-25T16:00:00.000Z`。
- **UTC ↔ 站点日期双向可还原**（含跨日边界：`15:59:59Z` 属前一日、`16:00Z` 属次日）。
- 未排期 → `dueAt/timezone` 均为 null（不伪造生成时区）。
- 非法时区/日期**一律拒绝**，不静默回退。
- 不同时区产出不同瞬时（Shanghai/Tokyo/UTC 三者各不相同），证明不是写死偏移量。
- **夏令时边界**：America/New_York 3 月切换前后偏移分别 UTC-5/UTC-4，且都能还原为原日期。
- 去重键：同输入同键、任一变化不同键、键内不含扫描时间。
- 复盘窗口：有序接受、单端允许、颠倒或非法拒绝。

### 2.2 K2 Kernel 集成测试（`apps/api/src/reminder/reminder.kernel.integration.test.ts`，8 项）

1. 日期型事项按站点时区当日 00:00 到期，UTC 与生成时区一并落库并可还原。
2. **重复扫描同一到期只产生一条发生记录**：连续三次 `recordDueOccurrence`，第二次起 `created=false` 且返回同一条记录，库内恒为 1 条。
3. **改期后旧到期不再触发**：延后两次后新到期正常产生记录，历史发生记录保留（2 条）；再用**旧**到期快照扫描仍 `created=false`，库内不增至 3 条。
4. 清空排期后 `plannedDate/dueAt` 皆 null，且拒绝为无到期事项记录发生（`action-has-no-due-at`）。
5. 非法时区与日期被拒。
6. 复盘关联事项与发布版本，记录行为/观察窗口/下一次尝试；同 `requestKey` 重放返回同一记录，列表恒为 1 条。
7. 复盘证据状态缺省 `UNKNOWN`；窗口颠倒、缺 `didWhat`、事项不存在分别被拒。
8. **旧 Action 行为保留**：未排期时无到期字段；完成/重开语义与既有字段不变。

### 2.3 HTTP 出口集成测试（`apps/api/src/reminder/reminder-http.integration.test.ts`，3 项）

真实 `AppModule` + 独立 SQLite，核验浏览器实际调用路径：

1. `POST /ops/reminders/resolve-due`：**匿名 401**，带管理 token 返回 `{ dueAt: '2026-09-25T16:00:00.000Z', timezone: 'Asia/Shanghai', source: 'date' }`。
2. 全链走通：`POST /actions`（带排期）→ 响应含推导出的 `dueAt/timezone` → `GET /ops/actions/:id/occurrences`（初始为空）→ `POST /ops/reviews` → 同 `requestKey` 重放返回同一 id 且列表仍 1 条 → `GET /ops/reviews/:id` 详情可读。
3. 非法时区经 HTTP 返回 **400**。
