# O10：验收一次真实运营回路

前置：O04、O05、O07、O08、O09、V24、C24。
落点：§10、一条非敏感演练记录或站主选定的真实内容记录。
验收：K1/K3；问题 → 更新事项 → 候选/审批 → 发布核验 → 复盘 → 下一事项全链可追；覆盖 A01、A14–A15、A20、A28，不编造增长结果。

## 1. 真实运营回路设计与演练（端到端八阶段）

演练基于真实内容标识 `o10-real-loop-article`，采用真实 SQLite 数据库与领域内核接线，串联自访客前台提问到最终复盘与下一动作生成的全生命周期闭环：

### 阶段 1：真实访客提问（A01 访客交互）
- 访客就跨平台运维文章发起提问：`请问文章中提到的自动化脚本如何在 Windows 下执行？能否补充说明？`；
- 助手回复并完成送达确认（`delivery=ack`，生成成功 ≠ 已送达，访客真实收到）；
- 正本未受影响，未自动触发选题或修改正本。

### 阶段 2：显式转为更新事项（A28 访客问题转事项 / O05）
- 站主查看访客提问，调用预览获取纯文本摘要；
- 显式点击创建更新事项，设置排期日期 `2026-10-01`；
- 事项保存**软引用**（`entityType=CONVERSATION`, `entityId=convId`），正本不复制会话全文，会话删除后事项依然保留；
- 经共享单一时间规则推导 `dueAt` 为 `2026-09-30T16:00:00.000Z`。

### 阶段 3：提醒到期扫描与处置（O02 / O03）
- 模拟时间推移触发到期扫描（`ReminderScanService.scanOnce`），准确领取到期未完成事项并生成 `ReminderOccurrence`；
- 站主显式处置该到期提醒：首先延后（snooze）至 `2026-10-04`，原到期瞬时原子重算失效；
- 站主完成改动后标记完成（complete），事项状态变更为 `DONE`，到期清空避免重复被扫。

### 阶段 4：内容变更、候选审批与受控写入（A11 / A12 / C05 / C06）
- 站主受控保存文章初始正本（通过 A02 门禁字段要求）；
- 针对访客问题生成包含 `Windows 运行适配` 小节的候选内容（独立候选文件仓储）；
- 创建并批准候选变更（绑定 L1 授权），原子执行 `applyApprovedChange` 写入正本，原文件正本哈希确证更新。

### 阶段 5：发布预检、阶段流转与线上确证（A16 / C12 / C14 / C16 / C17）
- 执行实际发布范围预检（`preflight`），确认门禁字段齐全且生成稳定清单；
- 计算公开版本身份（public projection hash）；
- 准备发布记录并推进发布阶段状态机：`PREPARED → COMMITTING → PUSHED → VERIFYING`；
- 线上核验器确证目标哈希匹配，更新发布阶段为 `PUBLISHED`；
- 自动同步公开问答快照并切换指针（`assistantIndexState: 'SYNCED'`）。

### 阶段 6：内容更新复盘（A14 / A15 / O08）
- 关联已完成的 Action 与刚发布的 `release.id` 创建复盘记录；
- 登记客观行为（didWhat）、观察结果（observed）、观察窗口（2026-09-27 至 2026-10-04）；
- 指标来源明确声明来自 `/ops/overview` 7d 统计，因样本量不足，证据充分度如实标注为 `INSUFFICIENT`（**绝不编造增长结果，样本不足写未知**）；
- 提出下一次尝试建议（nextAttempt：“下阶段增加交互式命令自测沙盒”）。

### 阶段 7：复盘建议显式转下一事项（O09）
- 站主显式将复盘的 `nextAttempt` 转为下一更新事项，排期至 `2026-10-15`；
- 新事项关联原复盘（`entityType=REVIEW, entityId=review.id`）；
- 基于 `requestKey` 幂等去重；
- 从新事项可准确回溯原复盘事实，形成完整的运营迭代闭环。

### 阶段 8：可追溯的运营统计确证（O06 / O07）
- 最终调用运营统计聚合接口 `/ops/overview?window=30d` 验证全链数据真实落库；
- 访客提问数、交付确认数、待处理事项数、已发布内容数全部与底层事实严格吻合，无任何假数据或假趋势。
