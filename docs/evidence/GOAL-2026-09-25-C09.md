# C09：实现精确审批与一次性消费

## 实施结果

- **精确审批契约与业务逻辑（`ContentMutationService.approve`）**：
  - **前置基线复检**：审批前复检正本内容；若磁盘正本当前 hash 与候选基线 `baseHash` 不一致（已被外部修改），抛出 409（`content-base-conflict`）拒绝批准。
  - **L2 授权复检（R08/R09）**：校验授权存在、未撤销、未到期、范围包含目标 slug，且显式持有 `content:approve` 权限。
  - **不可变审批绑定**：构造不可变 `ContentApproval<'apply-candidate'>`，固定 `{action, target, baseHash, candidateHash, grantId, grantRevision}` 及其 SHA-256 bindingHash。
  - **幂等批准**：相同授权重复调用 `approve` 幂等返回已批准事实；不同授权尝试篡改已批准候选返回 409 冲突拒绝。
  - **审计留痕**：通过 R05 `OperationsJournal` 事务记录 `content.candidate.approved` 审计日志。
- **执行前复检与原子消费（`ContentMutationService.apply`）**：
  - **执行前复检授权**：执行 `apply` 前重新核查绑定授权；若授权已被撤销（`revokedAt !== null`）、授权已过期或授权修订版本已变（`grant.revision !== binding.grantRevision`），审批即刻失效，拒绝执行（403 `grant-denied`）。
  - **执行前复检原文**：若在批准后、执行前正本已被修改导致当前 hash 不等于 `baseHash`，拒绝写入。
  - **原子消费审批**：调用 `beginApply`，在单个 SQLite 事务中将候选状态从 `APPROVED` 转为 `APPLYING` 并持久化 `content.apply.intent` 意图审计，原子消费该审批，避免并发重复消费。
  - **文件 CAS 与终态确认**：执行 C03 `expectedHash` CAS 写入文件；完成后在独立事务将状态记为 `APPLIED` 并写入结果审计。
  - **幂等执行**：已处于 `APPLIED` 状态的候选再次调用 `apply` 直接幂等返回，不重复写文件或重复记账。
  - **权限不自动外溢**：候选内容应用仅写入工作区正本，绝不包含 `publish-website`，不自动创建或触发任何发布流水线（严格遵守 A02）。
- **管理端 HTTP 端点**：
  - 在 `ContentChangeController` 中暴露 `POST /ops/content-changes/:id/approve` 与 `POST /ops/content-changes/:id/apply`，受全局 `AdminTokenMiddleware` 保护。
