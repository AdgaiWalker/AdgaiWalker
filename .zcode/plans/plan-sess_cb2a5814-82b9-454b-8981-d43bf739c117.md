# 需求信号中心（agent 日志分析 + harness 复用）

定位一句话：回答「访客到底在要什么，我该写什么/做什么」。数据已在积累（四张信号表每天在写，其中搜索 miss 与内容反馈是只写不读的暗数据），本方案不新建日志系统，只做聚合视图 + AI 归纳 + 行动闭环。

**第一设计原则（用户 2026-09-05 拍板）**：零比喻。后台就是工作室——从需求与内容，到产品与商业闭环。新界面只用直白词：需求、问题、搜索、反馈、选题、内容、产品；不出现题苗/线索/孵化等内部黑话。

## 做什么（两批 + 语言原则）

### T5.A L0 需求信号中心（零 AI，纯聚合，~半天）

1. **信号聚合 API** `GET /insights/signals?days=N`（管理侧，token 防线内）：
   合并四源输出统一形状 `{来源: 问了小影|卡口提问|搜索没找到|文章反馈, 文本, 时间}`——AssistantRun.question + Clue.body（卡口）+ SearchMiss.query + ContentFeedback(signal=needs-more, 含 note)
2. **相似问题频次**：轻量归一化（trim/大小写/去标点）计数排序；不做模糊聚类（量级不需要）
3. **admin「需求」页**（新）：
   - 信号流（四源合并倒序 + 来源标签）
   - 高频问题榜（TOP 20 + 频次）
   - 内容缺口区：搜索 miss 词 + 是否已有对应内容（对照 content.json 标题/标签做简单匹配）
   - 现有「助手问题」页并入为需求页的一个分区（保留逐条转选题，按钮文案改「转选题」，走现有 POST /seeds 链路，人工点击红线不破）

### T5.B AI 需求周报（harness 复用，~半天）

4. **分析 Run**：需求页「分析本周」按钮 → Nest 经现有 harness 适配器（WALKER_DSH_RUNTIME_BIN 基建零新增）跑一次分析：
   - 输入：本周四源信号聚合快照 + 站内内容标题清单
   - harness 可挂只读工具反查内容库（验证「这个需求是否已有文章」——找缺口的关键能力，裸 API 做不到；这也是选 harness 而非直连的理由）
   - 输出走 Run 合同模式（版本化 JSON，校验后采信）：主题归纳（TOP 主题 + 代表问题 + 频次）、内容缺口、**建议分类**——对齐工作室价值链：写文章 / 做产品 / 自媒体选题 / 商业信号
   - 分析过程本身有 Run 追溯（harness 价值）
5. **周报持久化**：新表 `InsightReport`（id, weekOf, inputSnapshot, report, createdAt）——本方案唯一新表，历史可回看
6. **触发**：仅手动按钮，零新基建（探索确认全站无 cron；有价值再自动化）

### T5.C 周报 UI + 行动闭环（~半天）

7. 需求页周报区：最新周报 + 历史列表；每条建议带「转选题」按钮（人工确认进现有题苗链路）
8. 全链路测试 + 语言零比喻审查

## 不做什么（Razor）

- ❌ 不建信号新表（四源只加视图）；仅新增 InsightReport（周报产物必须有地方存）
- ❌ 不做实时 AI 打标（每条入库即跑 LLM）、向量聚类、全站浏览埋点（post.read）、cron
- ❌ 不自动转选题（红线：AI 不主选）
- ❌ 本批不动 admin 现有其他页的比喻文案（线索/题苗等旧页语言重组另立一批，避免摊子过大）

## 验收

- 需求页：四源信号可见、高频榜有数、miss 缺口标注正确；旧问题池功能无损并入
- 「分析本周」产出真实周报（主题/缺口/建议四分类），历史可回看，Run 可追溯
- 建议可人工转选题；typecheck + 三端测试 + 管理接口 token 防线验证绿
- 新界面零比喻词审查通过
